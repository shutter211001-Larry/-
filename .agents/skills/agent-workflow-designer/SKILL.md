# Agent 工作流設計師

將「幫我完成某件事」整理成一條有來源、有檢查點、能重跑的工作路徑。避免直接跳到一段看似完整的提示詞。

## 先理解這次工作

從現有對話與專案檔案取得資訊，缺少會改變方向的內容才詢問：目的、對象、交付成果、必須保留的內容、專案規則與素材、目標工具，以及成功標準。把無法確認的內容列為假設。

## 建立 Agent 的工作路徑

1. **讀取脈絡**：先讀適用的 `AGENTS.md`、專案說明、既有 Skills、素材規範和輸出位置。
2. **尋找方法**：涉及產品、模型、標準或工具時，優先找目標產品的官方文件；官方沒有清楚方法時，再找原始研究或可重現案例。
3. **判斷適用性**：記錄來源、日期、適用版本／任務、依據與限制。分清官方建議、範例、測試結果與推論。
4. **拆解工作**：把高階需求拆成輸入、決策、執行步驟、交付物、檢查點與失敗處理。
5. **先交付計畫**：在高成本、外部發布或方向尚未確認前，先交付來源判讀、需求摘要、執行計畫和預期成果。
6. **執行與驗證**：完成後依原始目標與明示標準檢查，不以「工具成功執行」代替成果驗收。
7. **沉澱方法**：只把已驗證、可跨任務重用的做法寫進 Skill 或 `AGENTS.md`；這次特有的 brief、素材與結果留在 Project。

## 決定寫在哪裡

| 內容 | 建議位置 |
|---|---|
| 整個專案都要遵守的品質、命名與驗收規則 | `AGENTS.md` |
| 特定類型任務的可重用步驟與判斷方式 | `.agents/skills/<name>/SKILL.md` |
| 這一次的需求、素材、來源與結果 | Project 內的 brief／工作檔 |
| 只對單次執行有效的補充 | 當次對話或任務筆記 |

以「能獨立產生有價值成果的任務」作為 Skill 邊界，不為每個小動作各建一個 Skill。

## 輸出格式

以繁體中文交付：

1. 需求摘要：目的、受眾、成果、限制、假設。
2. 資料與方法：要讀什麼、查什麼、如何判斷可信與適用。
3. Agent 工作流：輸入 → 分析 → 執行 → 檢查 → 保存。
4. 檢查點：何時需要使用者決定，何時可由 Agent 自主完成。
5. 驗收標準：完成的證據與失敗時的處理。
6. 保存建議：哪些寫入 `AGENTS.md`、Skill 或本次 Project。

若使用者要求實作，建立所需檔案並驗證路徑與格式；不要只回傳範例文字。

## 品質原則

- 指令說明目的與判斷依據，讓 Agent 能處理變化，不靠僵硬咒語。
- 研究與執行分開：先確認方法適用，再讓工具產生結果。
- 高成本或不可逆步驟安排確認點；一般可逆工作可由 Agent 直接完成。
- 驗收回到原始目標，不只檢查格式或檔案是否存在。
- 每次迭代優先改一個主要變因，記錄改動與結果。
