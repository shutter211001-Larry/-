# ComfyUI Doc Scraper

本技能專為協助使用者查詢、統整並翻譯 ComfyUI 最新文件與節點說明而設計。由於目標受眾為**設計師與行銷人員**（參見 `AGENTS.md` 的專案設計準則），因此在查詢完技術文件後，必須將艱澀的程式碼或參數轉換為他們能聽懂的「生活化比喻」。

## 技能目標與執行步驟

當使用者要求查詢 ComfyUI 的文件、節點、或工作流範例時，請依循以下標準步驟：

### 1. 鎖定資訊來源 (Search Phase)
請優先使用 `search_web` 與 `read_url_content` 工具，針對以下官方或權威性來源進行搜尋：
- **ComfyUI 官方文檔**: `https://docs.comfy.org/` (搜尋節點、核心架構、API)
- **ComfyUI 官方 GitHub**: `https://github.com/comfyanonymous/ComfyUI` (查看最新 Releases 或 Examples)
- **ComfyUI 社群 Wiki 或討論區**: 用於搜尋特定工作流 (Workflow) 或節點組合範例。

*Tip: 搜尋時可加入 `site:docs.comfy.org` 等語法以提高精準度。*

### 2. 資訊萃取與轉譯 (Extraction & Translation Phase)
找到相關說明後，不要直接把英文或工程師寫的說明丟給使用者。你必須進行「術語轉譯」：
- 將冰冷的技術參數翻譯為直覺理解的「生活化比喻」。
  - *範例：KSampler 不要只說是取樣器，可以比喻為「靈魂畫師在畫布上來回塗改的次數」。*
  - *範例：CFG 不要只說是 classifier-free guidance，可以比喻為「AI 聽話的程度 / 靈感發散度」。*
- 提取「**痛點 > 名詞解釋 > 功能 > 示範 > 實作**」的邏輯來重構這段知識（依循本專案的教學風格）。

### 3. 產出報告結構 (Output Format)
請以 Markdown 格式產出統整報告。請嚴格遵守以下範本結構：

```markdown
# 📚 ComfyUI 知識卡：[查詢的主題/節點名稱]

## 1. 這是什麼？(名詞解釋與生活化比喻)
- **官方定義**：[簡述官方定義]
- **生活化比喻**：[用設計師聽得懂的例子解釋，例如把 VAE 比喻為底片沖洗室]

## 2. 什麼時候會用到？(痛點與場景)
- [描述一個設計師常遇到的痛點或災難，例如：產出的圖色彩灰暗，因為忘記加 VAE]

## 3. 參數怎麼調？(功能與避坑 TIP)
- **[參數 A]**：建議設定在 [數值區間]。
  - ⚠️ **避坑 TIP (新手大坑)**：[說明調錯會發生什麼事]
- **[參數 B]**：...

## 4. 參考範例 (Examples)
- [列出官方推薦的接法或工作流範例 (Workflow)]

## 5. 參考資料來源
- [來源文章的連結 1]
- [來源文章的連結 2]
```

## 注意事項 (Rule Check)
- **嚴禁**給出過期的 SD1.5 舊資訊，除非使用者特別要求，否則請優先針對 SDXL / FLUX 等當前主流模型提供說明。
- 如果找不到精準的官方文件，請誠實告知，並提供相關的社群討論作為替代方案。
- 在介紹觀念前，必須先舉出生動或崩潰的案例來建立記憶點。
