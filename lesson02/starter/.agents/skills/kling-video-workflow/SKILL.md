# Kling 影片工作流

1. 讀取工作區規則、任務說明、圖片與既有影片；摘要主體、用途、動作、限制和輸出格式。
2. 查 Kling 官方文件中與目前模式相符的提示詞方法。記錄標題、網址、查閱日期、適用模式與限制。
3. 找不到官方明確建議時，才補充可重現案例，並清楚標示證據層級。
4. 呼叫 `who_am_i` 取得當下可用模型、參數與工具規格。不要把教材或記憶中的模型名稱當成固定設定。
5. 依來源、素材和 MCP 回傳規格，選擇文字生影片、一般圖片生成影片、Omni 多圖參考、首尾幀或參考影片。不要把不同模式或其他模型的公式直接搬用。
   - **文字生成影片**：文字要建立主體、主體動作與場景，再按需加入攝影機、光線與氣氛。
   - **一般圖片生成影片**：圖片已提供主體與場景，文字集中描述「主體＋動作；背景＋動作」。使用簡單句，避免要求明顯偏離圖片狀態的複雜動作。
   - **Kling 3.0 Omni 多圖參考**：依 `who_am_i` 回傳的欄位上傳圖片，在提示詞以 `图片1`、`图片2` 等名稱明確引用。逐張說明用途，但把角色分工視為待驗證控制策略，不假設模型一定完全隔離各張參考圖。
   - **Kling 3.0 Omni 多鏡**：需要多鏡敘事時，依目前規格開啟多鏡，按 `Shot 1 (秒數)`、`Shot 2 (秒數)` 寫景別、角度、敘事、攝影機與切換。商品保真或微距除錯時先關閉多鏡，一次只測一個主要效果與一個攝影機動作；這是測試策略，不是模型能力限制。
6. 若任務是商品或微距鏡頭，先把商品輪廓、標籤保留、生成新文字、材質反光、液體物理、對焦落點、淺景深邊緣與鏡頭路徑列成獨立驗收項目。不要用「主體一致」或「電影感」一句話帶過。
7. 先交付來源判讀、需求摘要、提示詞草稿、MCP 工具計畫與小測試方式。任何會消耗點數的生成都要先取得使用者確認。
8. 本機素材先用 `file_upload`（檔案上傳工具）取得 Kling 可讀的網址，再呼叫對應的生成工具。圖片生成影片使用 `image_to_video`。
9. 保存生成工具回傳的 `generationId`（生成任務編號），用 `query_tasks`（任務查詢工具）追蹤同一筆任務。等待期間不可重複送出相同生成；完成後從 `works[].url`（成果網址欄位）取得成果並保存到專案。
10. 生成後檢查主體與品牌一致、動作清楚、鏡頭合理、結尾可用、沒有不需要的新物件。商品微距還要在開頭、四分之一、中央、四分之三與結尾逐幀檢查輪廓、標籤、材質、焦點與反光連續性。
11. 每輪只改一個主要變因，記錄提示詞、參數、生成任務編號、變更與結果。把已驗證的通用方法更新到本 Skill；本次特有內容留在任務說明。
12. 如果同一商品連續出現相同偏差，停止堆疊形容詞。先查直接針對該能力的評測或官方工作流，再提出替代方案；把官方能力說明、獨立評測、實際測試與尚未驗證的推論分開記錄。
13. 若要判斷 Kling 是否比其他模型弱，固定同一份中文創意意圖、素材、片長、比例與驗收標準，再依每個模型的官方文件產生模型專用提示詞；不要強迫所有模型使用相同字串。單鏡頭先測 5—6 秒，每個模型至少三次。把「保留首幀已有標籤」與「依文字生成新標籤」分開評分，並分別記錄對焦、景深邊緣、材質反光、鏡頭路徑和商品穩定。

## 提交前的證據標示

交付提示詞與工具計畫時，把每一項方法標成：

- **官方支援**：Kling 官方文件或本次 `who_am_i` 明確列出的輸入、參數或模式。
- **專案策略**：為了商品保真、除錯或檔案管理而採用的工作方式，例如先關閉多鏡，或把商品、背景、特效拆成三類參考圖。
- **待實測**：官方未保證，必須用本次商品結果驗收的主張，例如三類參考圖能否同時穩住標籤與水花。

不要把官方功能展示當成品質保證，也不要把專案策略寫成模型的硬性限制。

無法確認的模型、參數、帳號能力或回傳格式，先重新呼叫 `who_am_i`；仍無法確認時明確回報，不可猜測。
